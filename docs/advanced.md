## ۱. به‌روزرسانی خودکار و مقایسه دیجست در Docker Swarm

پس از هر push به شاخه `main`، پایپ‌لاین GitHub Actions دو ایمیج بک‌اند و فرانت‌اند را با تگ‌های `latest` و `<short-sha>` در مخزن GHCR منتشر می‌کند. رول `watchtower` یک عامل به‌روزرسانی سبک و سازگار با Swarm را روی نود Manager نصب می‌کند که هر ۵ دقیقه یک‌بار اجرا می‌شود:

```
+------------------+       Pull Image        +--------------------+
|  GitHub Registry | ----------------------> | Worker Node Cache  |
+------------------+                         +--------------------+
                                                        |
                                                Compare Digest
                                                        v
+------------------+      Rolling Update     +--------------------+
| Swarm Replicas   | <---------------------- | Digest Changed?    |
| (start-first)    |                         | 1. Run Migrations  |
+------------------+                         | 2. docker update   |
                                             +--------------------+
```

### چرخه اجرای خودکار:
1. تصویر `latest` سرویس‌های `backend` و `frontend` را از GHCR می‌کشد (`docker pull`).
2. دیجست تصویر کش‌شده محلی را با دیجست ثبت‌شده در `docker service inspect` مقایسه می‌کند.
3. اگر دیجست تغییر کرده باشد، ابتدا Migrationهای بک‌اند با همان تصویر جدید اجرا می‌شوند.
4. با دستور `docker service update --image <image>@sha256:<digest>` به‌روزرسانی به موتور Swarm سپرده می‌شود.
5. استراتژی استقرار بر پایه `start-first` است؛ یعنی ابتدا کانتینر جدید اجرا و سالم‌سنجی می‌شود، سپس کانتینر قدیمی خاموش می‌گردد.
6. در صورت شکست Migration یا خطای اجرای کانتینر جدید، سرویس بک‌اند دست‌نخورده باقی مانده و فرانت‌اند نیز تا زمان پایداری بک‌اند به‌روزرسانی نخواهد شد.

> **نکته معماری:** کانتینر استاندارد Watchtower برای کانتینرهای مستقل طراحی شده و با Reconciler داخلی Docker Swarm دچار تداخل می‌شود. به همین دلیل در این پروژه از یک اسکریپت مانیتور دیجست Swarm-native استفاده شده است.

## ۲. قفل مشترک Ansible و Watchtower (جلوگیری از Race Condition)

برای جلوگیری از تداخل استقرار دستی توسط ادمین (Ansible) و استقرار خودکار دوره‌ای (Watchtower Agent)، مکانیزم قفل مشترک پیاده‌سازی شده است:

- **فایل قفل مشترک (`/srv/<project>/.deploy.lock`):** دستورات استقرار و اجرای Migration در پلی‌بوک‌های Ansible با فرمان `flock -w 900` تا ۱۵ دقیقه منتظر آزاد شدن قفل می‌مانند. عامل خودکار نیز با `flock -n` (Non-blocking) قفل را می‌سنجد؛ اگر سیستم در حال استقرار توسط Ansible باشد، عامل خودکار بدون خطا چرخه را رد کرده و در تیک ۵ دقیقه بعد مجدداً بررسی می‌کند.
- **پرچم وضعیت عملیاتی (`/srv/<project>/.deploy-in-progress`):** این فایل در ابتدای رول `application` ایجاد و در انتهای آن حذف می‌شود. این پرچم بازه زمانی میان دو مرحله قفل‌گیری (اجرای Migration و آپدیت استک) را پوشش می‌دهد. در صورتی که اجرای Ansible به هر دلیل متوقف شود، پرچم‌های قدیمی‌تر از ۳۰ دقیقه به‌صورت خودکار نادیده گرفته می‌شوند.
- **تگ‌های تغییرناپذیر (Immutable Tags):** عامل خودکار صرفاً سرویس‌هایی را رصد می‌کند که تگ آنها برابر متغیر `auto_update_tag` (پیش‌فرض `latest`) باشد. اگر ادمین با تعیین تگ مشخص (مانند یک commit sha خاص) یا اجرای `rollback.yml` سیستم را مستقر کند، عامل خودکار موقتاً به‌روزرسانی سرویس مذکور را متوقف می‌سازد تا مداخله دستی بازنویسی نشود.

## ۳. کنترل و مانیتورینگ تایمر و سرویس‌های Systemd

عامل خودکار به‌صورت تایمر و سرویس Native تحت نظارت Systemd مدیریت می‌شود.

### دستورات پرکاربرد مدیریت:
```bash
# بررسی وضعیت فعال بودن تایمر و زمان اجرای بعدی
sudo systemctl status liquid-portal-watchtower.timer

# بررسی لاگ آخرین اجرای سرویس
sudo systemctl status liquid-portal-watchtower.service

# مشاهده لاگ تصمیم‌های به‌روزرسانی (pull، مقایسه دیجست، مایگریشن و آپدیت)
tail -n 100 /srv/liquid-portal/auto-update.log

# توقف موقت به‌روزرسانی خودکار (مناسب زمان دیباگ یا نگهداری سرور)
sudo systemctl stop liquid-portal-watchtower.timer

# فعال‌سازی مجدد تایمر
sudo systemctl start liquid-portal-watchtower.timer

# اجرای دستی یکباره چرخه برای تست عملکرد
sudo systemctl start liquid-portal-watchtower.service
```

### متغیرهای قابل تنظیم در رول `watchtower`:

| نام متغیر              | مقدار پیش‌فرض | توضیح کاربردی                                                 |
| :--------------------- | :----------- | :------------------------------------------------------------ |
| `auto_update_enabled`  | `true`       | فعال یا غیرفعال‌سازی سراسری تایمر به‌روزرسانی خودکار            |
| `auto_update_interval` | `5min`       | فواصل زمانی بررسی GHCR (فرمت زمانی `OnUnitActiveSec` سیستم‌دی) |
| `auto_update_tag`      | `latest`     | تگ داکری هدف برای تعقیب؛ در صورت استقرار با SHA متوقف می‌شود   |

## ۴. امنیت عمیق توکن‌ها: مهلت انقضای هم‌زمانی و شناسایی سرقت

الگوی احراز هویت بدون وضعیت (Stateless) این سامانه مجهز به سیستم تشخیص نفوذ و چرخش توکن است:

```
Client Requests Rotation -> Server Generates New Token Pair
         │
         ├── New Token Issued & Old Token Marked Rotated
         │
         ├── Concurrent Requests within 10s (Grace Period)
         │   └── Returns Current Active Token (Prevents Race Issues)
         │
         └── Replay Request after 10s (Theft Detected!)
             └── Revokes Entire Token Family & Invalidates All Sessions
```

### مکانیزم‌های کلیدی:
1. **چرخش با قفل خانواده (Family Tracking):** با هر بار تمدید موفقیت‌آمیز، یک جفت کلید جدید ساخته شده و توکن قبلی به عنوان «استفاده‌شده» ثبت می‌شود. تمامی فرزندان یک زنجیره لاگین به یک شناسه ریشه (`family_id`) وابسته‌اند.
2. **مهلت انقضای هم‌زمانی ۱۰ ثانیه‌ای (Concurrency Grace Period):** اگر دو تب در مرورگر هم‌زمان درخواست تمدید بفرستند، شبکه تا ۱۰ ثانیه توکن جدید صادرشده را بازمی‌گرداند تا کاربر با خطای ناهماهنگی روبرو نشود.
3. **شناسایی سرقت و ابطال بلادرنگ (Theft Detection):** اگر یک Refresh Token که بیش از ۱۰ ثانیه از چرخش آن گذشته دوباره توسط کلاینتی ارائه شود، سیستم فرض می‌کند توکن به سرقت رفته و توسط هکر Replay شده است. بلافاصله تمامی توکن‌های متعلق به آن `family_id` باطل شده و کوکی کاربر پاک می‌شود.

## ۵. استراتژی پشتیبان‌گیری و بازیابی فاجعه (الگوی 7/4/6)

پشتیبان‌گیری پایگاه داده با اسکریپت‌های بهینه و امن انجام می‌گیرد و تابع قواعد دقیق نگهداری است:

- **الگوی نگهداری 7/4/6:**
  - نگهداری **۷** نسخه از بکاپ‌های روزانه اخیر (Daily)
  - نگهداری **۴** نسخه از بکاپ‌های هفتگی (Weekly)
  - نگهداری **۶** نسخه از بکاپ‌های ماهانه (Monthly)
  - تمامی نسخه‌های قدیمی‌تر به‌صورت خودکار حذف می‌شوند تا فضای دیسک پر نشود.
- **عملیات اتمیک با قفل flock:** اسکریپت `scripts/backup_postgres.sh` با قفل فایل اجرا می‌شود تا دو فرآیند بکاپ هم‌زمان ایجاد نشده و فرآیند ناقص نماند.
- **اعتبارسنجی با هش SHA-256:** در زمان ایجاد بکاپ، هش چک‌سام آن تولید شده و اسکریپت `scripts/verify_backup.sh` پیش از هرگونه استفاده، سلامت فایل و عدم خرابی دیسک را بررسی می‌کند.
- **آزمون ماهانه بازیابی ایزوله:** اسکریپت `scripts/test_restore_monthly.sh` هر ماه به‌صورت خودکار یک کانتینر موقت PostgreSQL مجزا بالا آورده، آخرین فایل بکاپ را در آن ری‌استور کرده و کوئری صحت داده می‌زند تا اطمینان حاصل شود داده‌ها قابل بازیابی هستند. (برای مطالعه سناریوهای بحران به [docs/disaster_recovery.md](disaster_recovery.md) مراجعه فرمایید).

## ۶. تنظیمات پیشرفته Ansible و استقرار عملیاتی

### نمونه اجرای سفارشی با تگ مشخص و تعداد رپلیکای دلخواه:
```bash
ansible-playbook -i inventory/production/hosts.yml playbooks/deploy.yml \
  -e "app_image_tag=v1.2.0 backend_replicas=6 frontend_replicas=4"
```

### استفاده از Ansible Vault برای متغیرهای محرمانه:
توصیه می‌شود متغیرهای `jwt_secret`، `refresh_token_secret` و `db_password` در فایلی نظیر `inventory/production/group_vars/all/vault.yml` قرار گرفته و رمزنگاری شوند:
```bash
ansible-vault encrypt inventory/production/group_vars/all/vault.yml
```
سپس در زمان اجرای پلی‌بوک از فلگ `--vault-password-file` استفاده نمایید.
